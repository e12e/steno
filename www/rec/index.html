I. The Instrument & Its Premise

Local Transcription Without External Telemetry

Modern institutional and project meetings routinely involve sensitive deliberations, personal data, or unpublished technical work that should not be transmitted to third-party cloud transcription APIs. Steno—a modern annalist for your meetings, an automaton stenographer (steno.py)—consolidates an entire speech-to-minutes pipeline into a single, self-bootstrapping Python file that executes exclusively on the operator’s own machine.

Once model weights are cached locally, every stage—from microphone capture and voice activity detection to word-level alignment, speaker diarization, and structured minutes generation—operates offline. Neither audio waveforms nor text transcripts leave the local filesystem.

II. The Five-Stage Checkpointed Pipeline

Crash-Resumable Stages & Speaker Attribution

Long audio jobs on consumer hardware are vulnerable to memory pressure, battery depletion, or manual interruption. Rather than treating transcription and summarization as a monolithic pass, the engine writes atomic JSON checkpoints under .mote_checkpoints/<stem>/ after each stage completes.

If a run is paused or interrupted, re-running the same file resumes automatically from the last completed checkpoint. Operators may also re-execute individual stages—such as regenerating meeting minutes with a different language model or updated manual notes—in seconds without repeating acoustic inference.

Stage 1 • ASR
Speech-to-Text (1_asr.json): Transcribes raw audio (.wav, .m4a, .opus, .mp3) via WhisperX using vocabulary hints extracted from the meeting title, participant list, and attached slide decks (.pptx, .pdf, .docx).
Stage 2 • Align
Word-Level Forced Alignment (2_align.json): Aligns every transcribed word to exact millisecond boundaries via Wav2Vec2 (using NbAiLab/nb-wav2vec2-300m-bokmaal for Norwegian small/base models).
Stage 3 • Diarize
Speaker Separation (3_diarize.json): Assigns words to distinct speaker clusters (SPEAKER_00, SPEAKER_01, …) via pyannote/speaker-diarization-community-1. Automatically bypassed when locked to a single speaker (--speakers 1) for lectures or keynotes.
Stage 4 • Names
Identity Mapping & Interactive HTML (4_speakers.json): Resolves speaker IDs to participant names using round-table introductions, direct address rules, and manual notes. Emits a searchable HTML transcript with browser-side speaker renaming and one-click HTML re-export.
Stage 5 • Notes
Minutes & Lecture Summaries (_referat.md / .html): Streams structured Markdown and printable HTML via a managed local Ollama instance, switching automatically between multi-speaker meeting minutes (with action tables) and single-speaker lecture notes.
III. Cross-Platform Execution & Localization

Operation on macOS, Windows, and Linux

The header of steno.py is a polyglot script valid under POSIX shells (/bin/sh), Windows Command Prompt / PowerShell, and direct Python invocation. On first launch, it verifies or installs Astral’s standalone uv binary, provisions an isolated Python 3.12 runtime with pywebview, markdown, and static-ffmpeg, and downloads standalone whisperx and ollama binaries on demand.

Both the progressive-disclosure desktop interface and the command-line parser provide full localization in English (en) and Norwegian (no). Launching without arguments opens the native desktop window; passing any file or flag dispatches directly to the command-line interface.

curl -LsSf https://s.hypertekst.net/rec/install.sh | sh

IV. Empirical Verification & Hardware Profiles

Synthetic Four-Speaker Benchmark

To prevent memory exhaustion on 8 GB and 16 GB laptops while maintaining word accuracy on Norwegian and English speech, models run sequentially rather than concurrently. WhisperX and alignment models are explicitly unloaded and garbage-collected before Pyannote or Ollama is initialized.

“Across twenty evaluated ASR and LLM combinations on a synthetic four-speaker benchmark suite, pairing a compact 244M acoustic model with a 300M phoneme aligner and a 4B local reasoning model outperformed models six times larger while running nearly three times faster.”

Before starting a job, the application evaluates available system RAM and disk space against the peak sequential memory requirement of the selected model pair, warning the operator if a lighter profile is required.
